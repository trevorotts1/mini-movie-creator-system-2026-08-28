## 0. PRODUCT DEFINITION

MMCS = Mini Movie Creator System: a production-ready, resumable, extensible AI
mini-movie / serialized-TV production engine. Pipeline: story idea → concept → script
development → character approval → storyboarding → media generation → QC → editing →
permanent asset archival → final rendering. Usable day one from Claude Code,
claude-nine, and OpenClaw via one canonical skill; architected so the same engine can
power a standalone application later without rewrite (§30).

Core value: persistent characters with exact canonical image references; series
continuity; intelligent scene/shot planning; model-aware prompt and reference
budgeting; controlled cost; durable media archival; automated QC with immediate
repair; deterministic Remotion/FFmpeg assembly; human approval at creative gates;
safe resumability; tool-independent core.

Names, exact: Claude-nine (never "Claude-9"), OpenClaw (never "Open Claude"), 9Router,
MMCS.

## 3. HUMAN APPROVAL GATES — EXACT STOP CONDITIONS

Six mandatory hard-stop gates. Nothing advances past a gate without explicit operator
sign-off; no interruption for minor technical choices (gates exist for
expensive/irreversible/creative decisions only):

1. **Concept** — developed concept presented; no screenplay work before approval.
2. **Script** — screenplay generated and QC'd; no cast/candidate work before approval.
3. **New character selection/lock** — candidate choice 1/2/3/Try Again; character
   locked only after approval (§9).
4. **Storyboard** — storyboard/keyframe plan approved; no paid generation before this.
5. **Rough cut** — assembled rough cut approved; only affected assets regenerate on
   revision; no final render before approval.
6. **Canon/Series Bible update** — proposed permanent continuity changes reviewed and
   approved after the episode (§10).

Separate from the 6 gates, the spend gate (§4) stops automatically at $25.00
cumulative. Trivial technical operations never gate.

## 4. COST / QUOTA ENGINE — $25 CUMULATIVE ATOMIC SPEND RULE

- Track per provider and model: requested seconds, generated seconds, accepted
  seconds, rejected seconds, retries, included quota usage, estimated cost, actual
  cost if returned, cumulative episode spend, cumulative daily spend.
- `AUTO_SPEND_LIMIT_USD = 25.00` (configurable). Rule: cumulative **projected paid
  spend < $25.00 → proceeds automatically**; a request that would reach/exceed
  $25.00 without prior authorization **requires user approval before crossing**.
- **Cumulative atomic budget reservation:** reservations are taken atomically against
  one shared ledger so five parallel workers cannot each reserve $24.99 and
  collectively spend $120. Reservation precedes submission (job state
  BUDGET_RESERVED, §18); release on failure/rejection.
- Cumulative relevant spend, not per-agent. Included subscription quota / free
  allowance tracked separately and never counted as paid spend.
- Cost estimates shown at the estimate gate before production generation; costs
  ledgered into the asset/task records (baseline doctrine: state derived cost BEFORE
  spending).

## 5. MODEL CAPABILITY REGISTRY — MANDATORY

One centralized, versioned, machine-readable registry; separate registries for
reasoning/vision LLMs, image models, video models, voice models (and storage
providers). Never scatter capability constants inside adapters.

Media model profile (required fields):

```ts
interface MediaModelCapability {
  provider: string; modelId: string; kind: 'image' | 'video';
  lastVerifiedAt: string; sourceUrls: string[];
  confidence: 'VERIFIED' | 'PROVISIONAL' | 'UNKNOWN';
  prompt: { hardMaxCharacters: number | null; recommendedMaxCharacters: number | null;
            negativePrompt: boolean | null };
  references: { maxImages: number | null; maxVideos: number | null; maxAudio: number | null;
                firstFrame: boolean; lastFrame: boolean; firstLastFrame: boolean;
                multimodalReferences: boolean; incompatibleCombinations: string[] };
  output: { minDurationSeconds: number | null; maxDurationSeconds: number | null;
            resolutions: string[]; aspectRatios: string[] };
  pricing: { unit: string | null; amount: number | null; currency: string };
}
```

Full LLM/storage profiles additionally carry model_family, model_type, mode flags
(text_to_image, image_to_image, text_to_video, image_to_video, first_frame_to_video,
first_last_frame_to_video, multimodal_reference_to_video, reference_video_supported),
constraints (mutually_exclusive_inputs, incompatible_parameters, file_size_limits),
pricing (pricing_unit, current_price, quota, overage).

Every value carries provenance: `confidence` + `lastVerifiedAt` + `sourceUrls`.
UNKNOWN is a valid, first-class value — never invent a number to replace UNKNOWN
(e.g., never invent an Agnes hard prompt ceiling because another model has one).
Runtime-observed overrides (CAP-010) may refine profiles but never silently rewrite a
VERIFIED value on one transient failure (see `mmcs providers verify`, §25).

**Pre-request validation order (all providers, every request):**
resolve capability profile → compile model-specific prompt → count characters exactly
→ compare against hard max when known → compress semantically if needed (§6) →
validate reference counts → validate mutually exclusive modes → validate
duration/resolution → estimate spend/quota (§4 reservation) → only then submit.

Initial video providers (adapters, never hard-coded branches; architecture allows new
models without engine redesign):
1. **Agnes Video 2.5 Flash** — planning assumptions (verify current docs at build
   time): 720p; 4–12s clips; up to 5 reference images; first/last-frame support; no
   reference-video input; hard prompt ceiling **UNKNOWN until verified**. Flash is
   valid FINAL footage when it passes QC — never auto-discarded as preview-only.
2. **Agnes Video 2.5 regular** — 4–12s; up to 5 reference images; reference-video
   support; 720p/960p/2K options per current docs; prompt ceiling UNKNOWN until
   verified.
3. **Kie.ai Seedance 2.0 Mini** — verify exact Kie schema at build time; generation
   modes tracked separately (first-frame I2V; first+last-frame I2V;
   multimodal-reference); never combine mutually exclusive modes; unstated numeric
   limits are UNKNOWN/PROVISIONAL, never invented.
4. **Kie.ai Wan 3.0** — verify live schema/pricing/limits before implementation and
   record results in the registry. Prior research baseline (verify, never trust over
   newer docs): prompt up to **20,000 chars**; up to 10 reference images; up to 5
   reference videos; up to 5 reference audio; up to 30s output; 480p/720p/1080p;
   first/last-frame modes incompatible with multimodal reference modes.

## 6. PROMPT CHARACTER BUDGET MANAGER

Critical subsystem. Before EVERY model request: compile the provider-specific prompt →
count actual characters → load the model's hard/soft capability from the registry →
validate the hard limit when known → if over, compress intelligently — never truncate
mid-instruction; preserve highest-priority information → store original prompt,
compiled prompt, and exact count together.

Prompt priority order (video shots; same ordering principle for image models):
1. character identity-critical detail
2. action
3. continuity-critical wardrobe/props
4. location
5. start/end state
6. camera framing
7. camera motion
8. lighting
9. visual style
10. secondary atmosphere

## 7. SCENE / SHOT PLANNING ALGORITHM

Narrative scenes are planned separately from generation shots (a 45-second scene is
typically 5–8 shots, e.g. 6s establishing / 8s medium close-up / 7s reaction / 10s
two-shot / 5s insert / 9s close-up). Implement ScenePlanner, ShotPlanner,
SceneVisualPackagePlanner, KeyframePlanner, ReferenceBudgetPlanner.

Per approved script, in order: identify scenes → characters per scene → resolve to
canonical Character Library IDs → resolve active identity/hair/wardrobe versions for
the episode's continuity point → resolve recurring location/prop masters → estimate
scene duration → break scenes into camera shots by dialogue / emotional / action
beats → keep shots inside the selected model's duration limits → decide visual source
type (§22) → decide keyframe/reference strategy (§8) → generate storyboard assets →
storyboard approval before any paid generation.

Shot planning inputs: dialogue beat; emotional beat; camera grammar; action;
continuity; selected video model duration; reference capabilities; generation
reliability; cost.

## 8. KEYFRAME / SCENE-MASTER CLASSIFICATION + REFERENCE BUDGET

**Keyframe classification per shot (mutually exclusive strategies):** zero keyframes
(text-to-video acceptable) · one starting keyframe (exact start identity/composition)
· start + end keyframes (exact start and end) · scene master + allowed references
(multi-character continuity where the model permits) · multimodal reference package
(complex scenes, only where the model supports it).

**Scene Master Image:** important multi-character scenes get one approved scene-master
image establishing identities, wardrobe, room/location, lighting, props, and physical
positions. Internal storyboard images are NOT provider input images — internal
planning may use more images than the provider receives.

**ReferenceBudgetPlanner — MINIMUM SUFFICIENT references per shot; never fill the
model's maximum just because it exists.** A single-character close-up often needs 1–2
references; medium/full shots identity + wardrobe/full-body + optional location;
two-character dialogue often beats many portraits with one precomposed approved scene
master; precise transitions use first/last keyframes when supported.

Score every candidate reference by: identity value; wardrobe value; location value;
prop value; pose/composition value; starting-state value; ending-state value;
model-specific historical success. Persist which references produced accepted vs
rejected clips so the planner learns best reference packs for recurring
characters/models.

## 9. CHARACTER LIBRARY

Global Character Library exists outside individual episodes; series link characters
from the global library into their cast.

- **Permanent IDs:** stable business IDs (`CHAR_MONICA_BENNETT_001` style), never
  display-name-keyed.
- **Canonical identity asset record (durable media linkage, not prose):** MMCS asset
  ID; character ID; identity version; GHL media file ID; GHL folder ID; durable GHL
  URL; SHA-256; local cache path if present; image dimensions; generation
  provider/model; source task/job ID; prompt; approval state; canonical flag. Example
  shape:

```json
{
  "characterId": "CHAR_MONICA_BENNETT_001",
  "displayName": "Monica Bennett",
  "identityVersion": "v1",
  "canonicalIdentityAsset": { "ghlFileId": "...", "ghlFolderId": "...",
                              "ghlUrl": "https://...", "sha256": "..." },
  "activeAppearance": { "hairVersion": "long-braids-v1", "wardrobeVersion": "business-blue-v1" },
  "voiceProfileId": "VOICE_MONICA_001"
}
```

- **3-candidate UX (exact):** script requires a new character → exactly 3 candidate
  designs → shown as Character 1 / 2 / 3 → user picks "1 / 2 / 3 / 4-Try Again" → Try
  Again creates three NEW candidates (previous rejected candidates kept only as
  draft/rejected, never reusable) → selection creates the full canonical reference
  pack → every approved reference archived to GHL → persist GHL file ID + URL + folder
  ID + SHA-256 + generation metadata → LOCK CHARACTER approval → only then CANONICAL.
  Rejected candidates are never used later.
- **Reference package categories:** Identity/ (face-front-master, face-3q-master,
  face-profile-master, full-body-master); Expressions/ (neutral, happy, angry,
  worried, surprised); Wardrobe/<wardrobe-version>/; Voice/ (fish-audio-profile,
  pronunciation-dictionary); Provider-Packs/ (agnes, seedance, wan). Incremental
  enrichment supported; not all categories required.
- **Asset states:** DRAFT → REVIEW → APPROVED → CANONICAL → RETIRED (plus REJECTED).
  Only APPROVED/CANONICAL assets auto-reuse.
- **Identity versioning (immutable history):** hairstyle/age/scars/body changes never
  overwrite history. Example: Monica identity v1 long braids S01E01–E08; v2 short hair
  effective S01E09 — historical episodes keep referencing the canon-at-the-time
  version. A hair/wardrobe change creates a new appearance version with effective
  episode/time and must not replace the base identity master.
- Canonical GHL file ID + URL + checksum are used verbatim in downstream reference
  plans and provider calls.

## 10. SERIES BIBLE + CANON APPROVAL

Persistent series canon independent of any LLM conversation: series premise; world
rules; characters; relationships; locations; wardrobe; props; visual style; camera
language; voice profiles; timeline; prior episode summaries; unresolved plot threads;
canon changes (versioned).

End of episode → **Proposed Canon Changes** review (e.g., Marcus broke his arm;
Monica moved apartments; Harris discovered the secret; Monica changed hairstyle). No
permanent canon update without user approval (Gate 6). Historical episodes reference
the canon state at their time.

## 17. GHL MEDIASTORE — DURABLE ARCHIVE

GHL Media Storage is the V1 durable archive. Temporary provider URLs are never
canonical long-term storage. Generic `MediaStore` abstraction +
`GoHighLevelMediaStore` implementation; later S3/R2/GCS without rewriting the
production engine.

**Folder tree (idempotent — search before create, never duplicate roots):**

```text
Convert and Flow/
  Character Library/
    <Character Name>/
      Identity Masters/ Expressions/ Wardrobe/ Voice References/ Approved Scene References/
  Series/
    <Series Name>/
      Series Bible/ (Characters/ Locations/ Wardrobe/ Props/)
      Season 01/
        S01E01 - <Episode Title>/
          01 Script/ 02 Characters/ 03 Scene Masters/ 04 Storyboards/ 05 Audio/
          06 Video Clips/ 07 Rough Cut/ 08 Final/ 09 QC Metadata/
  Standalone Movies/
    <Project Name>/ (same 01–09 subfolders)
```

**Auth:** `Authorization: Bearer <sub-account access token / private integration
token>`, `Version: v3` header. Never log the token.

**Exact request sequence:**
1. Find root/folder: `GET /medias/files` with location context (altType=location,
   altId) — search exact "Convert and Flow" before creating.
2. Create missing folder: `POST /medias/folder` `{altId, altType: "location", name,
   parentId?}` — persist the folder ID.
3. **Immediate archival:** provider generation completes → obtain temporary URL/file →
   immediately archive into the correct GHL folder via `POST /medias/upload-file`
   multipart (`hosted=true`, `fileUrl=<temp provider URL>`, `name=<deterministic
   canonical filename>`, `parentId=<episode/character folder>`) → store returned
   fileId + url → verify the GHL URL is reachable → mark ARCHIVED → only then treat
   the provider result as safely persisted.
4. **Fallback (remote ingest failure):** download immediately → checksum →
   ffprobe/decode verify → binary upload to GHL (25 MB general / 500 MB video limits)
   → verify returned ID/URL → integrity compare → ARCHIVED only after success.
5. Never regenerate expensive media merely because archival failed. Always persist the
   original provider task/job ID.

Before coding the adapter, inspect current official GHL Media Storage API docs (auth
method/scopes; location requirements; create-folder, list/search, upload-file
endpoints; hosted ingestion; size limits; response fields; rate limits/error
semantics) and record source URLs + last-verified date. Known facts (2026-08-28):
`GET /medias/files` lists files/folders; `POST /medias/folder` (altId, altType:
location, name, parentId); `POST /medias/upload-file` supports hosted=true + fileUrl,
returns fileId + storage URL; auth via sub-account token / private integration token;
Media Storage read/write permissions required.

## 18. ASYNC PROVIDER JOB SAFETY — IDEMPOTENCY STATES

Persist the provider task/job ID BEFORE polling. Per-job durable record: request
hash/idempotency identifier where supported; provider/model; task/job ID; request
params; submission timestamp; status; poll timestamp; result URL; archival status;
retry count.

State machine: `PLANNED → BUDGET_RESERVED → SUBMITTING → SUBMITTED → GENERATING →
GENERATED_TEMPORARY → ARCHIVING → ARCHIVED → QC_PENDING → (QC_FIXING →) APPROVED |
REJECTED`.

- Restart at SUBMITTED → resume polling the existing job; never resubmit; never
  double-spend.
- Restart at GENERATED_TEMPORARY → archive the known provider URL immediately if
  valid — never regenerate because an agent forgot; the URL/task ID lives in
  SQLite/state.

## 19. ASSET MANIFEST + NAMING

Every media asset has a durable DB record (never filenames/folders alone). Required
fields: `asset_id, series_id, episode_id, scene_id, shot_id, character_id,
character_version, asset_type, asset_state, provider, provider_model,
provider_task_id, original_provider_url, provider_url_expiration, ghl_file_id,

Deterministic human-readable filenames; provenance lives in the DB/manifest, not the

`character_monica_face_3q_master_v02.png`.

## 20. AUTOMATED QC + IMMEDIATE REPAIR

Every generated shot is QC'd before final use. Checks: correct character identity;
face consistency; skin tone; hair; wardrobe; accessories; body/anatomy artifacts;
props; location; lighting continuity; camera requirement; action requirement; visual
artifacts; lip/face problems; start/end state; neighboring-shot continuity; dialogue
suitability.

Video-capable multimodal models review video directly when possible; otherwise FFmpeg
extracts representative frames for image-vision QC. QC failure → **targeted
repair/regeneration of the affected shot only** per retry/cost policy — never blind
whole-episode regeneration. Retry routing policy per shot class: Agnes Flash
acceptance route → Agnes regular fallback → Seedance fallback → Wan hero/complex
fallback → human REVIEW state when automated routes exhaust. Final episode QC runs
before rough-cut presentation.

## 21. REMOTION + FFMPEG RESPONSIBILITIES

Remotion is the authoritative editing/timeline layer. No MoviePy as primary editor
(unless a later specific requirement cannot reasonably be solved with Remotion +
FFmpeg, and the blocker is documented).

- **Remotion owns:** timeline; clips; images; camera movement on stills; captions;
  titles; overlays; transitions; credits; graphics; music/SFX placement; rough-cut and
  final render compositions. Preserve the upstream shared kits, registry generation
  (`npm run gen`), frame-QA discipline (`frames.mjs` — dump frames, READ every PNG,
  checklists, local-frame conversion `local_f = global_s * fps − sequence_from`),
  `media/library` vs `media/projects` separation, and the six-beat grammar concepts.
  Convert the project to an episodic timeline (scene/shot compositions, generated-clip
  layer, still-motion layer, stock layer, native graphics layer, dialogue/captions,
  audio/music/SFX timeline, aspect-ratio support, rough cut, selective shot
  replacement, final render).
- **FFmpeg/ffprobe owns:** probing; transcoding; normalization; frame extraction;
  thumbnails/representative frames; audio utilities; integrity checks; compatible
  mux/encode.
- Rough cut → automated QC → present for approval (Gate 5) → individual shot
  replacement/trim/voice/music/caption correction → regenerate only affected assets →
  approval → final render → normalize/validate media (ffprobe passes) → final QC →
  archive final into `08 Final/` → production report (runtime; aspect ratio/resolution;
  providers/models used; generated/accepted/rejected seconds; retries; cost; quota
  usage; characters; canon changes; durable final URL; QC status). A 720p generated
  source upscaled to 1080p is never represented as native 1080p quality.

## 22. MEDIA TYPES — DO NOT GENERATE VIDEO FOR EVERY SECOND

## 28. BUILD PROCESS CONTRACT (orchestration discipline)

- **Lead-orchestrator prohibition:** the top-level session is ORCHESTRATOR ONLY —
  creates/assigns tasks, spawns visible workflows/agents, reads control plane/status,
  enforces dependency ordering and concurrency, stops/restarts/reassigns, instructs
  the merger and watchdog, reports. It MUST NOT write source, edit implementation
  files, write production tests, fix bugs, author adapters, implement
  CLI/DB/Remotion/GHL/skills, merge branches, resolve conflicts, or do QC fixes. If
  about to edit a production file, stop and delegate.
- **Visibility:** all work in visible workflows/agents; no hidden swarms; no
  fictitious concurrency; live ledger reflects actual agents; every active worker
  recorded in `state/agents.json`.
- **Limits:** max 10 agents per workflow (never 11+); max 500 concurrent globally
  (ceiling, not lifetime count). Maximize USEFUL concurrency — build the DAG, cover
  READY independent work, do not spawn idle agents.
- **Roles:** Builders = Opus role; Checkers/QC/Fixers = Sonnet role (request roles;
  claude-nine routes opus→opus-chain, sonnet→sonnet-chain; never rewrite the
  routing). Builders never self-approve; QC agents are FIXERS — defect found → fix
  immediately in the worktree → rerun tests → PASS or real-external-blocker. High-risk
  core/security/state-migration/merge changes get a second independent Sonnet checker.
- **Task ownership:** every real task has Task ID, workflow ID, builder, Sonnet
  QC/fixer, branch/worktree, owned path scope, acceptance criteria, status, test
  commands.
- **Worktree isolation:** branch `task/<task-id>-<slug>`; worktree
  `worktrees/<task-id>/` based on `origin/integration`. Builder + paired QC share the
  SAME task branch/worktree sequentially. Two tasks never own the same implementation
  file; shared-file collisions are split behind interfaces, sequenced narrowly, or
  given a dedicated integration task. Prefer generated registry fragments over
  high-contention single files.
- **Waves:** only real dependencies create later phases. Wave 0
  bootstrap/research/recovery infrastructure; Wave 1 all independent subsystems; Wave
  2 work truly needing Wave 1 (character → canonical GHL image → bible; screenplay →
  scene → shot → reference plan → model-specific request; provider result → GHL
  archival → QC → rough cut; CLI/Skill → engine APIs; resume across real provider job
  IDs); Wave 3 full-system integration, smoke production, release. Unlock dependents
  immediately.
- **Ten-minute loops:** `/loop 10m /mmcs-watchdog` and `/loop 10m /mmcs-batch-merge`
  (skills `.claude/skills/mmcs-watchdog/` and `.claude/skills/mmcs-batch-merge/`, do
  NOT set disable-model-invocation; SessionStart/recovery recreates them when absent;
  `.claude/loop.md` as emergency maintenance prompt). Watchdog: locks
  `state/locks/watchdog.lock`; verifies actual workflows/agents/worktrees vs recorded
  state; enforces 10/500; refills idle capacity IMMEDIATELY (never merely reports);
  pings/reassigns stalled agents; kills duplicates; ensures every BUILDER_DONE task
  has an active Sonnet QC; pushes PASS to merge queue; updates build-status.md +
  ledger + atomic checkpoint. Batch merge: locks `state/locks/merge.lock`; admits
  only Sonnet-QC-PASS items with passing tests; orders by dependency/conflict risk;
  merges batches to `integration` in a dedicated merge workflow; full affected-area
  regression + secret scan before push; conflicts resolved by visible conflict
  resolvers, never the lead; no QC PASS = no merge; main is promoted from integration
  only at milestone/release gates after full regression.
- **Control files at repo root:** `spec.md todo.md qc.md checklist.md ledger.md
  session.md recovery.md decisions.md task-graph.md ownership.md
  integration-queue.md build-status.md`. Directories: `state/` (checkpoint.json,
  workflows.json, agents.json, tasks.json, dependencies.json, merge-queue.json,
  costs.json, capabilities.json, recovery.json, locks/), `logs/` (watchdog/, merges/,
  qc/, sessions/), `worktrees/`, `scripts/orchestration/`, `.claude/` (hooks/,
  skills/). ledger.md is append-only (`timestamp | TASK-ID | agent | STATE | note`)
  and records: workflow/agent creation, task transitions, blockers, QC
  defects/fixes, capability decisions, API discrepancies, merges, rollbacks, test
  failures, checkpoints, restarts, user approvals, cost-threshold events, security
  issues.
- **Durable checkpoint:** `state/checkpoint.json` (schemaVersion, project, repoRoot,
  origin, upstream, integrationBranch, wave, task IDs by state, workflow/agent IDs,
  last watchdog/merge/regression timestamps, lastKnownGoodCommit, next actions).
  Atomic write (temp + rename) at every material task transition, before/after
  compaction, before/after batch merge, before planned restart, session end, after
  recovery, every watchdog cycle.
- **Hooks (all 8 events CONFIRMED in this CLI's schema):**
  `.claude/hooks/{session-start,pre-compact,post-compact,task-completed,teammate-idle,session-end}.sh`
  (executable) wired in `.claude/settings.json`. PreCompact: save-first-compact-second
  (checkpoint lock, session.md, checkpoint.json, ledger PRECOMPACT_CHECKPOINT,
  branches/worktrees/merge queue). TaskCompleted: exit 2 blocking when acceptance/QC
  evidence is missing (no ACTIVE→MERGED jumps). TeammateIdle: exit 2 with continue
  instruction when the teammate owns ACTIVE/QC_FIXING work; else allow idle.
  SessionStart: inject recovery context (orchestrator-only; read recovery set;
  reconcile worktrees vs records; recreate the two loops; never duplicate
  ACTIVE/PASS/MERGED tasks). SessionEnd: final checkpoint + exact resume state in
  recovery.md.
- **Recovery after restart:** `git status --short --branch; git worktree list; git
  branch --all --verbose`, then read in order: recovery.md, session.md,
  state/checkpoint.json, build-status.md, spec.md, task-graph.md, todo.md,
  checklist.md, qc.md (relevant), integration-queue.md, ownership.md, ledger tail
  (100–200 lines), session.md tail, then reconcile runtime vs disk. Never recreate a
  task whose branch already contains completed work. Restart loops. Orchestrator stays
  prohibited from implementing during recovery.
- **Bootstrap already done** (§2): repository, fork relationship, license, baseline
  verification exist. Remaining bootstrap work is control-plane completion + hook
  verification (`claude --debug-file logs/sessions/hooks-init.log --init-only`), not
  repo creation.
